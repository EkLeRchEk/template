# Trip Service

HTTP-сервис для управления поездками на Go. Проект разработан в рамках лабораторных работ №1 и №2.

Во второй лабораторной сервис переработан с использованием Clean Architecture, добавлены тесты и система наблюдаемости на базе OpenTelemetry.

## Технологии

- Go
- Chi — HTTP-маршрутизация
- PostgreSQL и pgxpool — хранение данных
- Squirrel — построение SQL-запросов
- Goose — миграции базы данных
- OpenAPI и oapi-codegen — HTTP-контракты
- OpenTelemetry — сбор трассировок, метрик и логов
- Jaeger — распределённые трассировки
- Prometheus — метрики
- Grafana — визуализация
- Loki — централизованные логи
- golangci-lint, gofumpt, gci — качество кода

## Возможности

- Создание поездки.
- Получение поездки по UUID.
- Завершение активной поездки.
- Сохранение истории изменения статусов.
- Запрет нескольких активных поездок для одного водителя.
- Транзакционная обработка операций с PostgreSQL.
- Проверки `/health` и `/ready`.
- Graceful shutdown HTTP-сервера.
- Структурированное JSON-логирование.
- Сбор метрик HTTP-запросов.
- Трассировка HTTP-запросов, бизнес-операций и запросов к PostgreSQL.

## Запуск

Для работы необходимы Go, Docker, tripgoctl и PostgreSQL.

### 1. Запуск окружения

```bash
tripgoctl environment start
tripgoctl connect
```

### 2. Настройка переменных окружения

Создать `.env` на основе `.env.example`.

Указать актуальный `DATABASE_URL` из вывода `tripgoctl connect`.

При использовании OpenTelemetry настроить:

```env
OTEL_SERVICE_NAME=trip-service
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:22318
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_RESOURCE_ATTRIBUTES=service.namespace=tripgo,deployment.environment=local
OTEL_TRACES_SAMPLER=parentbased_always_on
```

### 3. Применение миграций

```bash
make migrate
```

### 4. Запуск сервиса

```bash
make run
```

По умолчанию сервер доступен по адресу `http://localhost:8080`.

## Опрос устаревших поездок

Для получения актуальных координат поездок используется фоновый Worker Pool.

### Архитектура

Система работает по следующей схеме:

```text
PostgreSQL
    |
    v
Scanner (time.Ticker)
    |
    v
Bounded Queue (буферизованный канал)
    |
    v
Worker Pool (фиксированное количество горутин)
    |
    v
Push Gateway
    |
    v
Push Service
    |
    v
REQUEST_POSITION
```

Сканер периодически получает из PostgreSQL активные поездки,
для которых давно не поступали координаты.

Если координаты ещё не поступали, время отсчитывается от `started_at`.
Условие устаревания вычисляется непосредственно в SQL.

Поездки сортируются по времени последней активности:
первыми обрабатываются самые давно ожидающие координаты.

### Очередь и воркеры

Очередь реализована буферизованным каналом.
Количество воркеров фиксировано и задаётся через конфигурацию.

Для предотвращения повторного добавления одной поездки
используется структура `queued`, защищённая `sync.Mutex`.

Возможные результаты постановки задачи:

| Результат | Значение |
|---|---|
| `queued` | Задача успешно добавлена |
| `duplicate` | Поездка уже находится в очереди |
| `dropped` | Очередь заполнена, задача отброшена |

Постановка выполняется неблокирующим способом.
При переполнении очереди сканер продолжает работу,
увеличивается метрика `tripgo.stale_checks{result="dropped"}`,
а в лог записывается предупреждение.

Когда поступают новые координаты, ожидающая задача отменяется.
Если задача уже находится в канале, воркер проверяет её токен
и пропускает отменённую задачу.

### Конфигурация

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `POSITION_CHECK_INTERVAL` | `30s` | Интервал сканирования |
| `POSITION_STALE_AFTER` | `60s` | Время отсутствия координат |
| `POSITION_WORKERS` | `4` | Количество воркеров |
| `POSITION_QUEUE_SIZE` | `100` | Ёмкость очереди |
| `PUSH_HTTP_URL` | Задаётся окружением | Адрес Push Service |
| `PUSH_REQUEST_TIMEOUT` | `1s` | Таймаут одного Push-запроса |

### Отправка Push-запроса

Gateway отправляет HTTP-команду `REQUEST_POSITION`.

- `recipient_id` содержит идентификатор водителя (`driver_id`).
- `data.trip_id` содержит идентификатор поездки.
- Каждая отправка ограничена `PUSH_REQUEST_TIMEOUT`.
- При ошибке отправки воркер записывает предупреждение и продолжает работу.

Если координаты не поступили, поездка снова попадёт в выборку
при следующем сканировании.

### Graceful Shutdown

Остановка выполняется в следующем порядке:

1. HTTP-сервер прекращает принимать новые запросы и ожидает текущие.
2. Сканер останавливается, новые задачи больше не создаются.
3. Очередь закрывается.
4. Воркеры обрабатывают оставшиеся задачи в пределах `SHUTDOWN_TIMEOUT`.
5. При исчерпании таймаута отменяются выполняющиеся Push-запросы.
6. Закрывается HTTP-клиент Push Service.
7. Закрывается пул PostgreSQL.

После остановки фоновых компонентов не должно оставаться
неуправляемых горутин.

### Метрики

- `tripgo.stale_checks` — результаты сканирования и постановки задач.
- `tripgo.position_requests.queue.size` — размер очереди.
- `tripgo.position_requests.workers.active` — количество активных воркеров.
- `tripgo.position_requests` — результаты Push-запросов.
- `tripgo.position_requests.duration` — время обработки запроса.
- `tripgo.positions.saved` — количество сохранённых координат.

## HTTP API

| Метод | Маршрут | Описание |
|---|---|---|
| POST | `/api/v1/trips` | Создать поездку |
| GET | `/api/v1/trips/{tripId}` | Получить поездку |
| POST | `/api/v1/trips/{tripId}/finish` | Завершить поездку |
| GET | `/health` | Проверить работу сервиса |
| GET | `/ready` | Проверить готовность сервиса |

## Наблюдаемость

Приложение использует три сигнала OpenTelemetry.

**Трассировки:** Jaeger показывает цепочку выполнения HTTP-запросов, Usecase, транзакций и операций репозитория.

**Метрики:** Prometheus собирает количество запросов и время их обработки. В Grafana создан дашборд `Trip Service Monitoring` с показателями Request/s, HTTP Error Rate и HTTP Latency p95.

**Логи:** структурированные записи `slog` выводятся в терминал и экспортируются в Loki через OpenTelemetry Collector. Записи содержат Trace ID для связи с трассировками.

Адреса инструментов можно получить командой:

```bash
tripgoctl connect
```

## Тестирование

### Unit-тесты

Не требуют подключения к PostgreSQL.

```bash
make test
```

### Интеграционные тесты

Требуют запущенную PostgreSQL и применённые миграции.

```bash
make test-integration
```

Интеграционные тесты помечены директивой:

```go
//go:build integration
```

Проверяются жизненный цикл поездки, конкурентное завершение поездок, откат транзакций и повторное использование транзакции.

### Проверка качества кода

```bash
make check
```

Команда выполняет проверки форматирования через `gofumpt` и `gci`, запускает `golangci-lint`, `go vet`, unit-тесты с Race Detector и `git diff --check`.

Автоматическое форматирование:

```bash
make fmt
```

### Покрытие тестами

```bash
go test -cover ./...
```

Для измерения покрытия с интеграционными тестами:

```bash
go test -tags=integration -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```
