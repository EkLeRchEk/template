# Trip Service

HTTP-сервис для управления поездками, разработанный на Go в рамках лабораторной работы №1.

## Используемые технологии

- Go — язык программирования.
- Chi — HTTP-маршрутизатор.
- PostgreSQL — база данных.
- pgxpool — пул соединений с PostgreSQL.
- Squirrel — построение SQL-запросов.
- Goose — управление миграциями.
- oapi-codegen — генерация HTTP-интерфейсов по OpenAPI.

## Возможности

- Создание поездки.
- Получение поездки по UUID.
- Завершение активной поездки.
- Сохранение истории изменения статусов.
- Запрет нескольких активных поездок для одного водителя.
- Проверка состояния сервиса и подключения к БД.
- Корректное завершение сервера (graceful shutdown).

## Запуск проекта

Для запуска необходимы Go, Docker, tripgoctl и доступное окружение PostgreSQL.

### 1. Запустить окружение

```bash
tripgoctl environment start
tripgoctl connect
```

### 2. Настроить переменные окружения

Команда `tripgoctl environment start` автоматически создаёт файл
`.env` со всеми необходимыми настройками сервиса.

Используй созданный файл — повторно создавать `.env` из `.env.example`
не нужно.

Если запускаешь сервис вручную, без tripgoctl, создай `.env`
на основе `.env.example` и укажи актуальные настройки PostgreSQL.

### 3. Применить миграции

```bash
make migrate
```

### 4. Запустить сервер

```bash
make run
```

По умолчанию сервер доступен по адресу `http://localhost:8080`.

## HTTP API

| Метод | Адрес | Назначение |
|---|---|---|
| POST | `/api/v1/trips` | Создать поездку |
| GET | `/api/v1/trips/{tripId}` | Получить поездку |
| POST | `/api/v1/trips/{tripId}/finish` | Завершить поездку |
| GET | `/health` | Проверить работу сервиса |
| GET | `/ready` | Проверить готовность сервиса и БД |

## Архитектура работы с транзакциями

### Уровень изоляции Read Committed

Для выполнения транзакций используется уровень изоляции `Read Committed`.

Он гарантирует, что транзакция не увидит незакоммиченные изменения других транзакций. При этом каждый SQL-запрос внутри транзакции видит изменения, которые были зафиксированы до начала выполнения этого запроса.

Данный уровень изоляции выбран потому, что операции сервиса достаточно простые: создание поездки, завершение поездки и сохранение истории изменения её статуса. Для обеспечения целостности данных в этих операциях используются транзакции и ограничения PostgreSQL.

Более строгий уровень изоляции `Serializable` не требуется, поскольку основное ограничение конкурентного доступа — запрет нескольких активных поездок одного водителя — обеспечивается непосредственно базой данных с помощью уникального частичного индекса.

### Менеджер транзакций (TxManager)

Для управления транзакциями реализован отдельный компонент `TxManager`, расположенный в пакете `internal/database`.

Он предоставляет метод `Do`, который принимает контекст и функцию с бизнес-операцией.

Алгоритм работы:

1. Проверяется, существует ли уже транзакция в переданном контексте.
2. Если транзакция существует, операция выполняется в ней без создания новой транзакции.
3. Если транзакции нет, создаётся новая транзакция с уровнем изоляции `Read Committed`.
4. Транзакция сохраняется в `context.Context`, чтобы репозиторий мог использовать её при выполнении SQL-запросов.
5. Выполняется переданная бизнес-операция.
6. Если операция завершилась ошибкой, транзакция откатывается (`Rollback`).
7. Если операция завершилась успешно, изменения фиксируются (`Commit`).

Дополнительно используется отложенный вызов `Rollback`, который обеспечивает откат незавершённой транзакции, в том числе при возникновении паники.

**Использование транзакций в сервисе:**

- При создании поездки в одной транзакции сохраняются сама поездка и первоначальная запись в истории статусов.
- При завершении поездки в одной транзакции изменяется её статус и добавляется запись в историю изменений.

Таким образом, связанные изменения либо сохраняются полностью, либо откатываются целиком. Это предотвращает ситуации, когда поездка создана без записи в истории или завершена без соответствующего изменения истории статусов.

### Защита от нескольких активных поездок одного водителя

Для предотвращения создания нескольких активных поездок одним водителем используется механизм частичного уникального индекса PostgreSQL.

В миграции `20260924075242_create_trips.sql` создаётся индекс:

```sql
CREATE UNIQUE INDEX trips_driver_active_unique_idx
    ON trips (driver_id)
    WHERE status = 'active';
```

Он обеспечивает уникальность `driver_id` только среди записей со статусом `active`.

Это означает, что:
- один водитель не может иметь две активные поездки одновременно;
- после завершения поездки водитель может получить новую;
- завершённые поездки не мешают созданию последующих поездок.

Проверка выполняется непосредственно базой данных, поэтому ограничение сохраняется даже при одновременном поступлении нескольких запросов.

Если два запроса пытаются создать активную поездку для одного водителя, PostgreSQL обеспечивает соблюдение уникальности индекса: только одна операция сможет успешно зафиксировать такую запись. Вторая получит ошибку нарушения уникальности, если первая транзакция завершится успешно.

В репозитории эта ошибка преобразуется в доменную ошибку `ErrDriverBusy`. HTTP-обработчик распознаёт её и возвращает клиенту ответ `409 Conflict`.

Таким образом, защита от конкурентного создания поездок обеспечивается на уровне базы данных, а не только проверками в Go-коде.

### Рекомендации по таймаутам транзакций

При работе с транзакциями важно ограничивать время их выполнения.

Рекомендуется:
- использовать `context.WithTimeout` для ограничения времени выполнения транзакции;
- устанавливать таймаут транзакции с учётом общего времени обработки HTTP-запроса;
- задавать таймауты SQL-запросов не больше общего времени выполнения транзакции;
- не выполнять длительные внешние операции внутри транзакций;
- своевременно выполнять `Commit` или `Rollback`, чтобы не удерживать соединения PostgreSQL без необходимости.

В текущей реализации `TxManager` использует переданный `context.Context` при создании и фиксации транзакции, но отдельный таймаут внутри самого менеджера не устанавливает. Поэтому вызывающая сторона должна передавать контекст с подходящим ограничением времени выполнения.

Также желательно ограничивать время выполнения операции отката отдельным контекстом, чтобы завершение транзакции не могло ожидать бесконечно.
